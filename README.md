# Adversarial RL for Alert Prioritization in Fraud Detection

This project implements a game-theoretic framework for robust alert prioritization in fraud detection, combining **Adversarial Reinforcement Learning (ARL)** with the **Double Oracle** algorithm.

## Project Overview

The core objective is to compute an optimal stochastic policy for a defender to prioritize alerts, assuming a strong adversary who knows the defender's policy and dynamically chooses optimal attacks. The interaction is modeled as a zero-sum game, solved iteratively to find an approximate Mixed-Strategy Nash Equilibrium (MSNE).

## Dataset

The implementation uses the **Credit Card Fraud Detection** dataset from Kaggle.
- **Dataset URL**: [Kaggle - Credit Card Fraud Detection](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud)
- **Description**: Contains transactions made by credit cards in September 2013 by European cardholders. It presents transactions that occurred in two days, where 482 frauds are recorded out of 284,807 transactions.

## Key Hyperparameters & Information Alignment

This implementation is strictly aligned with the paper's specifications:
- **Information Constraints**: The defender operates under **Partial Observability**, seeing only alert counts ($N$), while the adversary has full visibility ($N, M, S$).
- **Network Architecture**: 
    - **Actor**: 16 hidden units (Fraud), Tanh activation, Xavier initialization.
    - **Critic**: 32 hidden units (Fraud), ReLU hidden activation, Linear output, He Normal initialization.
- **RL Parameters**: Discount factor 0.95, Actor LR 0.001, Critic LR 0.002, Buffer 40,000.

## Technical Documentation

### Core Environment (`AlertDetectionEnv.py`)
The `AlertDetectionEnv` class models the interaction between the defender and the adversary as a Markov Game.
- **State Space**: Represents counts of uninvestigated alerts ($N$), active attacks ($M$), and the source of each alert ($S$).
- **Defender Action**: Allocation of budget $B$ to investigate counts of different alert types.
- **Adversary Action**: Selection of attack types to execute within budget $D$.
- **Detection Logic**: An attack is detected if at least one of its generated alerts is in the set investigated by the defender.
    - **Hypergeometric Probability**: The probability of detection is modeled as $1 - P(\text{None of the } s_{at} \text{ alerts are chosen})$, where $s_{at}$ are the alerts generated by attack $a$ of type $t$. This is calculated using the Hypergeometric distribution: choosing $r_t$ (budget) alerts from $n_t$ (total) without picking any of the $s_{at}$ "target" alerts.

### Double Oracle Solver (`DoubleOracleSolver.py`)
The solver iteratively expands the set of pure strategies for both players.
- **MSNE Computation**: Uses `scipy.optimize.linprog` to solve the zero-sum game matrix at each iteration. This finds the optimal mixed strategy that minimizes the maximum possible utility an opponent can gain.
- **Best Response**: Instead of computing a strategy over all possible alert allocations (which is combinatorially explosive), the solver only adds strategies that are "Best Responses" to the opponent's current behavior, a process that converges toward the Nash Equilibrium.

### RL Oracles

#### DDPG-MIX (`paper_implementation/DDPG.py`)
- **Architecture**: Neural networks for both actor (policy) and critic (value function).
- **hidden units**: Tailored to the complexity of the case study (e.g., 16/32 units for Fraud detection).
- **Projection**: Since actors output in a continuous $[0,1]$ range, a scaling factor is applied to ensure the total investigation or attack cost does not exceed the allowed budget $B$ or $D$.

#### SGS (`improvement_experiments/SGS.py`)
- **Method**: Semi-Gradient n-step Sarsa with Linear Function Approximation.
- **n-step Sarsa**: Bridges the gap between Temporal Difference (TD) and Monte Carlo methods. By looking ahead $n$ steps before bootstrapping, it balances the bias of TD with the variance of Monte Carlo.
- **Semi-Gradient**: In function approximation, "semi-gradient" refers to only differentiating the prediction $Q(s,a; w)$ and treating the target (which also depends on $w$) as a fixed value during the update to ensure stability.
- **Features**: Polynomial basis features (degree-2) capture interactions between state components (e.g., alert counts) and action components.
### Parameter Derivation (`process_fraud_data.py`)
To make the simulation realistic, game parameters are derived from the real-world Credit Card dataset:
- **Attack Types (GMM)**: Fraudulent transactions are clustered into 3 types using a Gaussian Mixture Model based on PCA features ($V_1 \dots V_{28}$) and transaction amount.
- **Detection Probabilities ($P$)**: A Random Forest classifier is trained on genuine vs. fraudulent data. The probability $P(a,t)$ is derived from the fraction of fraudulent transactions that exceed specific classification thresholds.
- **False Alert Means ($F$)**: Calculated by applying the same Random Forest classifier to genuine transactions and counting how many "false positives" are generated at each threshold.
